# lwext4 patches

Applied automatically by the build (`make patch`, and as a prerequisite of every
object file). Idempotent — a clean checkout builds with a plain `make`.

**These files are the only copy of our changes to lwext4.** The submodule is
pinned at an upstream commit; anything edited into its working tree and not
written down here exists on one machine and nowhere else. `make check-patches`
replays the whole set onto the pinned commit in a temporary directory and
diffs the result against `Core/lwext4`, so that cannot go unnoticed again — it
had happened twice by the time it was checked, and both times the build was
green.

Two rules follow from `git apply` being all-or-nothing:

* **A patch may not disturb another patch's context.** Adding a line in the
  middle of a hunk an earlier patch already touched means that earlier patch
  can no longer be checked on its own, and the build's per-patch "is this still
  applied?" test starts failing on a tree that is perfectly correct. 0016 put
  an `#include` between two lines of 0010's context and did exactly this.
* **Regenerate a patch against the patches before it, not against the working
  tree.** 0014 was first produced as a whole-tree diff, so it carried hunks
  belonging to 0005 and 0008. Applied in order those hunks were already
  present, the patch failed as a unit, and the build skipped it with a note —
  a clone got a driver with no write barrier and no visible error.

| Patch | What it does |
|---|---|
| `0001-guard-EXT_FINCOM_IGNORED` | Lets the build extend the INCOMPAT bits lwext4 tolerates, so we can accept `metadata_csum_seed` (which modern `mke2fs` enables by default) after the bridge has verified the seed still matches the UUID. |
| `0002-fix-xattr-remove-ibody-finder` | **Bug fix.** NULL dereference (SIGSEGV) when removing an xattr stored in the inode body — the common case. |
| `0003-avoid-null-pointer-arithmetic-in-xattr-list` | Replaces a `sizeof`-via-null-pointer idiom that UBSan flags on every `listxattr`. |
| `0004-fix-htree-leaf-block-init-and-checksum-order` | **Bug fix.** New HTree leaf blocks were never cleared (stale buffer contents written into a directory block) and were checksummed before the last field was written, so `e2fsck` reported `directory passes checks but fails checksum`. |
| `0005-keep-journal-sequence-monotonic-across-mounts` | **Bug fix, data loss.** `jbd_journal_stop()` reset the on-disk journal sequence to 0, so every session restarted at 1 and stale log records from an earlier session were indistinguishable from current ones. A crash in the window after the journal superblock is published but before the transaction commits let recovery replay **old metadata over the live filesystem**. |
| `0006-do-not-fake-an-error-flag-while-mounted` | **Bug fix.** lwext4 marked a mounted volume by setting the superblock's `ERROR_FS` bit, so any volume that lost power came back reading *"not clean with errors"* even though nothing had gone wrong — and a clean unmount then cleared a genuine error flag. Now it clears `VALID_FS` on mount and ORs it back on unmount, which is what Linux does. |
| `0007-assert-must-not-spin-forever` | **Bug fix, availability.** A failed `ext4_assert` ran `while (1);`. On a mounted volume that means the driver stops answering while still holding the mount: every process touching it enters uninterruptible wait, `umount` hangs, and only `SIGKILL` clears it — at 100% CPU throughout. Now it aborts, so the mount is torn down and callers get `EIO`. |
| `0008-treat-block-zero-as-a-hole-not-a-block` | **Bug fix.** Block 0 is ext4's hole marker, but `ext4_block_get_noread()` accepted it, cached a buffer with `lb_id == 0`, and then tripped `ext4_assert(b->lb_id)` on release — reaching 0007's infinite loop. A lookup in a directory with a hole, or in an inode freed underneath a stale reference, wedged the whole driver. |
| `0009-clamp-the-last-block-groups-free-count` | **Bug fix.** `mkfs` gave every block group `blocks_per_group` free blocks, including a final partial one, so any volume that was not an exact multiple of the group size came out of `mkfs` with a free-block count that was too high — and `e2fsck` reported `Free blocks count wrong` on a brand-new filesystem. |
| `0010-set-the-bitmap-tail-padding-mkfs-writes` | **Conformance, not a bug fix.** `mkfs` wrote block and inode bitmaps as all zeroes; `mke2fs` sets the bits past the end of the group. Verified *not* load-bearing once 0011 is applied — kept so the on-disk result matches the reference implementation rather than relying on nobody reading those bits. |
| `0011-inodes-per-group-must-be-a-multiple-of-8` | **Bug fix.** `inodes_per_group` was aligned only to the inode-table stride (`block_size / inode_size`), which is 4 for 1 KiB blocks with 256-byte inodes. ext4 requires a multiple of 8 so each group's inode bitmap starts on a byte boundary; without it `e2fsck` reports `Padding at end of inode bitmap is not set`. `mke2fs` masks off the low three bits for the same reason. |
| `0012-honour-the-stored-metadata-checksum-seed` | **Bug fix, corruption.** Every metadata checksum was seeded with `crc32c(~0, uuid)`. ext4 stores the seed explicitly in `s_checksum_seed` when `metadata_csum_seed` is set — which `mke2fs` enables by default — precisely so that `tune2fs -U` can change a volume's UUID without rewriting every checksum on it. The two agree until somebody does that, and then *every* checksum lwext4 writes is wrong: `e2fsck` reports nine invalid group descriptor and inode checksums after a single `mkdir`. The bridge used to force such volumes read-only to avoid it; they are now writable. |
| `0013-an-inode-with-no-xattr-header-is-not-an-io-error` | **Bug fix.** `ext4_xattr_ibody_find_entry()` reported `EIO` for an inode whose in-inode attribute area carried no header — the ordinary state of almost every file — because `ext4_xattr_is_ibody_valid()` folds "absent" together with "malformed". Absence is now "not found"; corruption still returns `EIO`. The set path had been *relying* on that error to know when to lay a header down, so it now asks directly; without that it dereferences NULL on the first attribute written to a bare inode. |
| `0014-give-the-journal-a-write-barrier` | **Bug fix, corruption.** `struct ext4_blockdev_iface` had no way to ask the medium to commit, so jbd wrote a transaction and the commit block that vouches for it with nothing between them, and checkpointed with nothing between that and the commit. A drive is free to reorder all three. On a disk image this never shows — writes reach APFS through the page cache in issue order — while a USB stick pulled from under a live mount came back inconsistent five times out of five. Adds an optional `flush` to the interface and calls it on both sides of `jbd_trans_write_commit_block`. A NULL `flush` leaves jbd behaving exactly as before. |
| `0015-write-the-commit-checksum-big-endian` | **Bug fix.** lwext4 wrote the journal commit block's checksum in host byte order and verified it against `to_be32()` of the same computation, so on a little-endian machine it rejected every commit block it had written — as does Linux, which requires big-endian throughout the journal. That is why journal checksums looked unimplemented; it was one missing byte swap. |
| `0016-turn-journal-checksums-on-at-format-time` | **Conformance and defence in depth.** `mkfs` wrote a bare JBD superblock: no feature bits, no checksum type, no uuid, so the journal it laid down was the 1998 format. Sets `JBD_FEATURE_INCOMPAT_CSUM_V3` with crc32c, as `mke2fs` has by default for years, and copies the filesystem uuid into the journal superblock — the checksums are seeded from it, so without that every one computes against zeroes and Linux rejects the journal. A checksummed journal is the only defence against firmware that reports a cache flush without performing one, which no barrier can help with: recovery stops at the first commit block that does not verify, losing that change, instead of replaying a half-written transaction over a live filesystem. |
| `0017-checksum-the-tag-sequence-big-endian` | **Bug fix.** CSUM_V3 tag checksums covered the host-order sequence number where jbd2 checksums `cpu_to_be32(sequence)` — self-consistent, so lwext4 recovered its own journals, and wrong for everyone else: the Linux kernel rejected every data block of every transaction (`JBD2: Invalid checksum recovering data block…`), so a volume this driver left dirty could not be mounted by Linux at all. Same family as 0015: the journal is big-endian, including inside checksum computations. |
| `0018-the-revoke-count-is-records-not-reservations` | **Bug fix.** With checksums on, the revoke block's `count` folded in the 4-byte checksum-tail reservation, so every reader — lwext4, e2fsck, the Linux kernel — parses one entry past the last real one, into unset bytes: a fabricated revoke of an arbitrary block, silently installed on every recovery. Measured: sixty revoke blocks from a delete-heavy run, sixty garbage final entries. `Tests/run_revoke_tests.sh` is the red-first test. |
| `0019-revoke-what-you-free-not-what-you-remember` | **Bug fix.** Revokes were emitted only for blocks with a live `block_rec` — still tracked by an uncheckpointed transaction. The replayable log reaches further back than the checkpoint queue: a block journaled, checkpointed, freed, and reused as file data got no revoke, and replay clobbers it. Now every free is revoked, as Linux does; re-journaling in the same transaction still cancels it. Also the precondition for 0020's lazy tail. |
| `0020-advance-the-log-tail-lazily-and-durably` | **Bug fix, corruption.** The log tail was written on every checkpoint completion with no barrier — a tail that reached the medium before its checkpoint left the change in neither the log nor its home, and one that was lost while the freed log space was reused left recovery replaying nothing (both measured via the trace classifier). Now jbd2's shape: the tail is staged in memory and written durably only where the world must agree with it — the wrap path and the lap guard (barrier, superblock, barrier, once per ring cycle), stop, and recovery. Steady state is cheaper than before. |
| `0021-a-failed-checkpoint-read-is-not-an-invariant-violation` | **Bug fix, availability.** `jbd_journal_flush_trans` asserted that reading a log block back succeeds; pull the medium under a live mount and unmount's checkpoint flush hits the assert — SIGABRT mid-teardown (measured, USB yank during a write flood). The flush now returns the error and the purge stops rather than retrying a transaction that can never complete. The unflushed transaction stays covered by the staged tail, so the next mount replays it — which is what recovery is for. |
| `0022-block-zero-is-a-real-block` | Untangles three meanings of "block 0": the release-time validity assert now checks the buffer pointer (not `lb_id`), the hole-marker refusal from 0008 stays for every mapping-derived fetch, and `ext4_block_get_sb()` is the one sanctioned door to the superblock's home block — it computes the lba itself, so no caller-supplied hole can reach it. |
| `0023-journal-the-superblock` | **Bug fix, data loss.** `ext4_sb_write_trans()` commits superblock updates atomically with their transaction — `s_last_orphan` published separately from the unlink it points at stranded an inode at four consecutive cut points. The direct `ext4_sb_write` becomes cache-coherent, and `jbd_recover` reloads the superblock after replay (the 1 KiB-block path restored the disk but left the in-memory copy stale, and cleanup then undid the replay). jbd's tag-0 replay branch existed upstream, unreachable; it has a writer now. Kernel-verified at every cut. |
| `0024-format-with-metadata-checksums` | **Conformance, defence in depth.** mkfs stripped `metadata_csum`; now it formats with it, plus the frozen `s_checksum_seed`, matching mke2fs defaults. Most structures were already checksummed by the runtime code mkfs reuses; the real gaps were the superblock copies (each checksums itself after its `block_group_index` stamp — also an ordering requirement, since mkfs re-opens its own volume mid-format and verifies), the backup descriptor tables (checksummed at build time so every copy inherits), and the seed. `GDT_CSUM` stays stripped: mutually exclusive with metadata_csum. |
| `0025-unwritten-extents-gain-a-writer` | **New capability, plus two latent bugs.** lwext4 could read unwritten extents and even convert them, but nothing could create one — `ext4_extent_preallocate` (backing `F_PREALLOCATE`) and `ext4_extent_probe` add the writer and an honest map. En route: both merge predicates now refuse to merge a written extent with an unwritten one (upstream's would, silently marking data unwritten or garbage written), and `ext4_ext_zero_unwritten_range` zeroes direct-to-disk with a cache invalidate instead of through the journalled cache, where a later flush could clobber it and data blocks bloated the journal. Truncate learned that a size-0 file can still own blocks. Disclosure, merge and leak all suite-tested; every crash cut kernel-replayed. |
| `0026-route-assert-through-a-host-handler` | **Observability.** `CONFIG_DEBUG_ASSERT` ships enabled and the assert handler printed to stdout before aborting — which a sandboxed FSKit extension does not have, so the one message naming the broken invariant was invisible exactly where it mattered. `ext4_assert_failed` now calls an extern `ext4b_assert_fail()` the shim provides (os_log in the appex, stderr in the tool). Still fail-stop, deliberately; only the reporting moved. |
| `0027-recovery-reads-the-journal-in-runs-not-blocks` | **Bug fix, availability.** Journal replay read the log one 4 KiB block per device command; a real USB stick priced a 128 MiB journal at eight-plus minutes and DiskArbitration timed the mount out at ~20 s, so the volume never appeared. The recovery pass now reads the log through a 1 MiB read-ahead window in physically-contiguous runs, one command each — it is the one reader that knows its access pattern is a linear sweep. Scan and revoke passes keep per-block reads (they skip the data between headers). Measured on the incident's shape: 43k read commands down to 10k. `Tests/run_replay_speed_tests.sh` is the red-first test, pricing recovery like the medium that produced the incident. |
| `0028-replay-write-back-is-sorted-deduplicated-and-coalesced` | **Bug fix, availability — the other half of 0027's hang.** Every replayed block was flushed through the block cache one command at a time, in log order, and a hot metadata block logged in two hundred transactions was written two hundred times. Replayed blocks now collect in a 4 MiB batch, flushed sorted by target with only the newest copy of each block, one command per contiguous run. Cache-resident targets are rewritten in place so no stale dirty copy outlives the direct write. Also stops losing replay write errors — a failed flush now fails `jbd_recover` and leaves the journal to try again, where before the error vanished inside a `void` callback and the journal was cleared regardless. Measured: 29k write commands (120 MB) down to 2k (29 MB). |
| `0029-a-log-with-no-revokes-skips-the-revoke-pass` | **Availability.** The revoke pass re-walks every header block of the log to build a tree that is empty whenever the crashed session freed no journaled metadata — the common case for removable media (files copied on, nothing deleted). The scan pass, which walks at least as far, counts revoke blocks; zero skips the second walk. Halves the post-0027 header reads on a revoke-free log; a log with revokes walks all three passes unchanged. |
| `0030-replay-reports-every-failure` | **Bug fix, data loss.** Three exits of the tag-replay callback still returned silently after 0028's error channel; the live one is the journaled-superblock branch, where a refused write was followed by reloading the stale superblock from the medium and clearing RECOVER over it — the journaled content (an orphan-list head) gone behind a mount that reported success. All three now fail recovery, keeping the journal for the retry. `Tests/run_eio_tests.sh` sweeps an EIO across every superblock write of a recovery mount. |
| `0031-a-failed-checkpoint-stays-in-the-log` | **Bug fix, data loss.** `jbd_trans_end_write` recorded home-write failures in `trans->error` and *nothing ever read it*: the count completed, the tail advanced, and the journal stopped covering a block that never landed. Measured with the bad-sector model: forty files created, script exits 0, needs_recovery cleared, e2fsck finds all forty inodes "deleted/unused". The tail now stops at an errored transaction; everything behind it stays covered. Structurally the replay bug (0028/0030), on the checkpoint side — and what a mid-checkpoint device pull leaves behind. |
| `0032-stop-does-not-clear-what-it-could-not-flush` | **Bug fix, data loss.** `jbd_journal_stop` cleared EXT4_FINCOM_RECOVER and published start=0 even when the purge had broken off on a checkpoint it could not read (0021) or write home (0031) — the change then existed in neither the log nor its home. A non-empty checkpoint queue now skips the superblock writes entirely and returns the first recorded error; the next mount replays. ASan caught the teardown calling completion callbacks on freed memory; they are unhooked first. |
| `0033-the-cache-remembers-a-failed-write-back` | **Bug fix, silent failure.** The release-time flush in `ext4_bcache_free` is where nearly every metadata write in a non-write-back session reaches the device — and its result was discarded unconditionally. A failed buffer stays dirty but on no list the flush entry points walk, so the error could outrun every later flush and end in "ejected clean". A one-int latch records the first swallowed error; `ext4_block_cache_flush` folds it into its return and `ext4_umount` reads it after the cleanup sweep. Red cell: ext2 create onto a bad sector — before, exit 0 and an image e2fsck rejects. |
| `0034-mkfs-fails-when-its-writes-do` | **Bug fix, silent failure.** mkfs builds the volume in write-back mode, making its teardown the write path; the results of `ext4_fs_fini` and of leaving write-back mode were both discarded. mkfs's own mid-format verification catches most dying media first (honest note in the prose); this closes the remainder — a failure after the last verification read, on a block verification does not cover. |
| `0035-the-journal-geometry-is-checked-before-it-is-believed` | **Bug fix, memory safety.** The journal superblock's blocksize/maxlen/first/start were believed unbounded. An oversized blocksize turned every checksum pass into an out-of-bounds read and the checksum helper into an out-of-bounds *write* (it zeroes the tail in place), on every descriptor block of every recovery. The CRC cannot defend it — a crafted image checksums itself consistently, and mke2fs journals without metadata_csum carry no CRC at all. One check at the door in `jbd_get_fs`. Red cells in `Tests/run_bounds_tests.sh` under a deadline. |
| `0036-a-revoke-block-counts-only-its-own-records` | **Bug fix, memory safety.** 0018 fixed what the revoke `count` means; nothing bounded what it says. `count` below the header size underflows the unsigned subtraction to ~2^30 fabricated entries — reads past the block, a heap allocation each, then abort, at mount. A count outside [header, blocksize] now contributes no entries, like a failed checksum. |
| `0037-a-zero-length-dirent-cannot-loop` | **Hardening.** The predecessor walk in `ext4_dir_remove_entry` spins forever on a zero on-disk rec_len (wedged executor, force-eject) and asserted — abort() — on a chain that fails to tile the block. Both are now EIO. Honest note: the linear lookup path is shielded by `ext4_dir_find_in_block`'s own zero-guard; the exposed route is the htree leaf path, which the B14 fuzzing tranche covers properly. Precedent: 0007. |
| `0038-an-io-failure-is-an-error-not-an-invariant` | **Bug fix, availability.** Five asserts fired on plain I/O failure — freeing across a group boundary after an EIO, a full journal ring whose emergency purge failed (0021/0031's legitimate cases), the abort-rollback's two block fetches, and the replay revoke tree's allocation (which a hostile revoke count could manufacture). Each was the whole driver aborting on a failing medium; each is now an error to the caller. The journal allocator returns 0 — a block no valid caller can mean — and the get-wrappers refuse it. |
| `0039-checkpoint-completion-does-not-eat-its-own-queue` | **Bug fix, memory safety — latent upstream, found by 0035/0036's fixtures.** Completing one checkpointed buffer cascades into completing other pending copies of the same block, retiring whole transactions and freeing their structures — while three walkers held prefetched next-pointers across the cascade (measured heap-use-after-free on the pre-session build: 4 MiB mke2fs journal, ring wrap, power-cut load). Drain loops that re-read the queue head, a snapshot in `jbd_journal_cp_trans`, and two lifetime fixes (`remove_block_rec` refuses to free a record buffers still queue on; `end_write` clears the buffer callback before the cascade). ASan-clean both ways. |
| `0040-inode-tables-zero-in-runs-not-blocks` | **Availability.** The contiguous, all-zero inode table went through the cache one 4 KiB command at a time: ~66,000 commands per 16 GB format, and the same loop runs at *mount* on mke2fs `lazy_itable_init` volumes — inside DiskArbitration's budget, with each block also traveling the journal. Now one command per 1 MiB run, past the cache; crash-safe by idempotence (the UNINIT flag commits behind a barrier after the zeroes). Measured: 2 GB format 8,300 → 105 commands; dirty lazy volume's recovery mount ~7,000 → 77. Bounds in `Tests/run_format_tests.sh`. |
| `0041-checkpoints-go-through-the-replay-batcher` | **Availability + bug fix.** The unmount/ring-wrap checkpoint read each logged block with one command and wrote it home with another; it now uses 0027's window (capped to the transaction's span) and 0028's sorted/deduped batch. Rides along: the latent escape bug (a from-the-log checkpoint wrote escaped bytes home — the bit now travels on the jbd_buf), 0031's tail-freeze preserved through the rewrite, 0039's lifetime discipline (the transaction is lifted off the queue for the completion drain). Honest sizing note in the prose: eager release-flush already kept ordinary ejects small; this owns the uncommon cases. |
| `0042-recovery-reports-its-shape` | **Observability.** The incident took eight minutes to replay with nothing anywhere saying how deep the log was. jbd_recover now publishes transactions/blocks-replayed/log-size on `fs->last_recovery`; the bridge logs them with the duration — the one line that answers "where did the mount's time go" from os_log. |
| `0043-a-checkpoint-must-not-resurrect-an-older-copy` | **Data-loss fix (regression in 0041).** The replay batch's cache-sync — right for recovery, where the log outranks any resident — was inherited by the checkpoint path, where the ranking reverses: flushing an older transaction synced its stale logged copy over a newer transaction's dirty resident and cleared BC_DIRTY, so the newest copy of every hot block (inode tables first) could land one transaction stale under a green unmount, and later commits journaled the clobbered bytes. Found by e2fsck on a cleanly-unmounted mounted volume (root link count one short); a checkpoint's sync now leaves dirty residents alone. Cell: `run_write_tests.sh` "a checkpointed hot block keeps its newest copy". |
| `0044-a-purge-that-flushes-must-also-retire` | **Availability + data-loss fix (regression in 0041).** The allocator's one-shot purge flushed the head transaction and returned without retiring it, so the tail never moved and the ring never drained: sustained small-file work refused 273 of 1800 operations with ENOSPC on a volume 17% full, and a crash on such a full ring leaves a log neither we nor the Linux kernel can fully replay. The purge now re-inspects after flushing, which retires the transaction and frees the log space its caller is about to look for. Cell: `run_replay_speed_tests.sh` "1800 operations through a ring that wraps ~15 times, none refused". |
| `0045-preallocated-writes-map-and-zero-in-runs` | **Availability.** macOS preallocates before a large copy, so every Finder copy writes into unwritten extents -- and both the mapping and the zeroing that conversion needs were done one block at a time. Measured on a LUKS2 USB stick: a 522 MB copy issued 128,406 write commands for 996 MB at 6.3 MB/s. `ext4_fs_append_inode_dblk_range` maps the caller's whole run in one call and `ext4_ext_zero_unwritten_range` zeroes in 1 MiB runs; the offline equivalent went 25,941 commands to 254. Fresh files gain one allocation per run too. |
| `0046-an-overwritten-range-is-marked-written-not-zeroed` | **Availability.** The other half of 0045: a preallocated range was zeroed and then immediately overwritten, so the medium carried every byte twice (994 MB for a 522 MB copy). What keeps a reader from seeing the previous owner's bytes is the order, not the zeroing -- an unwritten extent reads as zeros. `ext4_extent_map_range` locates a range without converting it and `ext4_extent_mark_written` converts it afterwards, so the data lands first and a crash in between leaves the extent unwritten. 254 commands/210 MB became 153/105 MB. Cell: `run_prealloc_tests.sh` "a cut write into preallocated space shows only new data or zeros". |
| `0047-the-journal-is-allocated-in-runs-at-format-time` | **Efficiency.** `create_journal_inode` was the last caller asking the extent layer for one block at a time — up to 32,768 tree walks and bitmap operations for a large journal, and an extent tree shaped by that pattern. It now uses 0045's range form, so an 8 GB format lays the journal down as a single extent, which is also what lets recovery read the log back in large runs. Device commands unchanged (mkfs runs write-back); this was CPU. |
| `0048-an-extent-header-is-bounded-before-it-is-believed` | **Memory safety, reachable from a plugged-in volume.** Extent headers state their own entry counts and nothing bounded `eh_max`, the stride to the checksum tail — 786 KB past a 4 KB block for 0xFFFF, read on every validation and written on the checksum path. The root header, living in the inode, never passed through the only caller of `ext4_ext_check` at all. AddressSanitizer: reading one file on such a volume is a heap-buffer-overflow in `ext4_ext_binsearch`, reached from a directory listing. `eh_max` is now bounded by the space it describes, depth capped at 5, and the root validated before the walk. Cell: `run_bounds_tests.sh` "a corrupt extent header is refused, not walked". |
| `0049-metadata-blocks-are-cleared-before-they-are-filled` | **Hygiene / defence in depth.** `block_get_noread` returns the cache slot as-is, so a partly-written new metadata block sends the remainder of whatever it held to disk and folds it into the block's checksum. Four sites missed the rule this file documents: the dx leaf split's data block, the new index node, `ext4_ext_split_node`, and `ext4_ext_grow_indepth`. Honest scope: an attempt to demonstrate a user-data leak found none — file data never enters the block cache — so this stops uninitialised heap reaching the medium rather than one file's bytes reaching another. |
| `0050-a-transaction-writes-its-journal-blocks-in-runs` | **Efficiency.** The commit path wrote every journal block as its own 4 KiB command (BC_TMP|BC_FLUSH forces a flush on release), while replay and checkpoint already used runs. A transaction's journal blocks are consecutive by construction, so the payload is now gathered and issued one command per contiguous run, bypassing the cache and invalidating any copy from an earlier lap. 2,000 small files: 27,930 → 20,518 writes; journal commands on a 500-file run 558 → 192. Gated on crash consistency (203/203 recovered), reordered writes, and the Linux differential. |
| `0051-a-format-leaves-the-inode-tables-to-be-initialised-on-use` | **Availability.** `init_bgs` took a reference to every block group, and taking a reference is what runs the lazy initialisation — so a format eagerly zeroed all 64 inode tables: 128 MB written as 2 MB bursts scattered 128 MB apart, which cheap flash answers with an erase cycle each (0.4 MB/s, four minutes for 8 GB on a DataTraveler). The descriptors already say the groups are uninitialised and the on-demand path already handles them, as mke2fs assumes. Only group 0 and the last group (whose bitmap carries the end-of-volume padding) are done up front. 372 writes/135 MB → 250/7 MB, e2fsck-clean before and after heavy use, and the Linux kernel writes into the result happily. |
| `0052-only-ext4-may-leave-a-group-underived` | **Correctness + availability, correcting 0051.** The UNINIT flags mean nothing without `uninit_bg`/`metadata_csum`, and e2fsck rejects them there — 0051 exposed that on 44 of the sweep's 117 combinations, because the eager walk had been clearing them before anyone looked. ext2/ext3 now keep the full walk and format exactly as before. On ext4, the per-group bitmap writes are also skipped: they are what the flags tell a reader to derive, and at 4 KiB each scattered 128 MB apart they were most of a format's time on a stick. 250 writes → 128. |
| `0053-a-descriptor-backup-goes-only-where-a-backup-belongs` | **Availability.** `write_bgroup_block` wrote the descriptor table into every block group, consulting `has_superblock()` only for the offset — so with `sparse_super` 55 of 64 copies landed where no reader looks. Each is a 4 KiB write at a different group's start, and scattered writes are what a format's time consists of once the inode tables stop being zeroed (122 of 128 writes were ≤4 KiB, 575 KB total, 90 s on a DataTraveler). 128 writes → 73. Known gap recorded in the patch: bitmaps left for derivation mark only padding, so `e2fsck -b` recovery reports differences it then repairs. |
| `0054-a-range-is-checked-against-the-volume-before-it-is-freed` | **Corruption.** `ext4_balloc_free_blocks` turned its arguments into a first and last group id by division and walked between them without establishing that the last group exists. A range overhanging the end of the volume — a corrupt extent, or an extent tree walked with a bad length — was walked as if those groups were there, crediting the superblock a bitmap block's worth of free space per iteration and writing it through the descriptor table's address arithmetic. Leaves a group claiming more free blocks than it holds, which is the state an 8 GB stick arrived in: three impossible groups, cached total past the volume size, allocation collapsed to eight-block runs. Refused, not clamped. Only reproducible on a **partial last group** — a volume whose size divides evenly by the group size has no overhang, and the cell passes against the unfixed core there. |
| `0055-a-three-way-extent-split-re-finds-between-its-two-halves` | **Corruption.** `ext4_ext_convert_to_initialized` splits an extent twice when the converted range sits in the middle of it, and `ext4_ext_split_extent_at` reads `(*ppath)[depth].extent` without looking it up — so when the first split grew the tree, the second rewrote the wrong extent and left an index disagreeing with its leaves ("invalid extent node"). Unreachable until 0046: the other branches split once, and the pre-existing caller converts from an extent's start. Preallocated writes convert the middle. 10 of 24 mounted-data runs corrupted before; 0 of 16 with the fast path compiled out, which located it. Linux re-finds at the same point for the same reason. **Measuring it needs a warm-up**: ~6 runs after an extension restart are clean on any build, and a 6-run bisect scored 0/6 on both arms. |
| `0056-a-volume-claims-the-extended-attributes-it-uses` | **Correctness.** mkfs never set `EXT4_FCOM_EXT_ATTR` while the driver writes xattr blocks, so every i_file_acl was illegal to e2fsck: three complaints per file (the pointer, the i_blocks counting it, the bitmap bit holding it) and a volume reporting "still has errors" with every byte of data intact. macOS attaches xattrs to nearly everything, so a Finder copy of 408 files produced 408 such inodes. mke2fs sets the flag by default — which is why the differential suite against Linux never saw it, its fixtures being mke2fs-made. |
| `0057-converted-runs-are-folded-back-together` | **Quality.** `ext4_ext_convert_to_initialized` splits an extent to change part of its state, so converting a preallocated file chunk by chunk left one extent per chunk — 3 MB in four where a plain write is one, 512 MB in 256 against ten. Since macOS preallocates before every Finder copy that was every copied file: e2fsck counts each as non-contiguous and asks to narrow the tree, and the depth is what exposed 0055. Now folded back with the existing `ext4_ext_can_append`, which refuses to merge across a written/unwritten boundary. 3 MB goes four extents → one. |
| `0058-a-tail-is-published-only-once-it-has-landed` | **Durability.** Two sites advanced `journal->published_start` right after `jbd_write_sb` without checking it. A failed write left the tail recorded as published — and the first branch only fires when published_start has fallen behind, so believing it abreast suppresses the write that would have fixed it, and recovery reads from a position the superblock does not name. Now moves only on EOK. Found by auditing the carried-over backlog, not from a failure. |
| `0059-a-warning-nobody-can-hear-is-not-a-check` | **Diagnostics.** `CONFIG_DEBUG_PRINTF` is off in every build (an appex has no stdout), so `ext4_dbg` compiled to nothing and all 22 "checksum failed" sites across seven files were silent — the volume paid to compute them and nobody heard the answer. WARN/ERROR now reach the shim logger. Turning them on immediately exposed 22 **false** ones per suite run: the in-inode extent root (`pblk 0`) was checksummed as though it were a block, comparing against whatever follows the 60-byte root. Only real blocks carry a tail, so only those are checked. Every suite now runs silent, and a cell in the offline and mounted suites asserts it stays that way. |
| `0060-a-bitmap-that-fails-its-checksum-is-not-written-through` | **Bug fix, corruption.** The seven bitmap sites in `ext4_balloc.c` and `ext4_ialloc.c` did not merely warn: on a failed verify they modified the bitmap, recomputed the checksum over the modified bytes and wrote that back — laundering a corrupt bitmap into one that verifies and destroying the evidence in the same breath, so even `e2fsck` then found nothing wrong. They now return `EIO` and modify nothing. Reads are untouched: the policy is refuse writes, allow reads, and these seven are reachable only from allocate and free. Refusing a free leaks the blocks or the inode until `e2fsck` reclaims them — the intended trade. Depends on 0059 having removed the last false positive first. |
| `0061-a-run-may-cross-a-block-group-here` | **Diagnostics.** A free whose range spanned two block groups warned, on the reasoning that without `flex_bg` a group starts with its own bitmaps so no run can reach into the next. True of `mke2fs`; not of the volumes this driver formats, which leave three blocks free at the head of every group. Measured: an extent three blocks into group 12 holds file data and `e2fsck` is clean, and the loop below the warning already frees multi-group ranges correctly. Only reachable once writes reserve space ahead of themselves — one write call's worth of blocks never reaches a boundary — and only audible since 0059. Matters because 0060's enforcement depends on this channel being quiet. |
| `0062-the-other-null-pointer-sizeof-in-the-xattr-block-loop` | **Undefined behaviour.** `ext4_xattr_list()` sizes its buffer twice -- once per loop, one for the entries in the inode body and one for the entries in the xattr block -- and 0003 replaced the `(char *)((T *)0 + 1) - (char *)(T *)0` idiom in only the first. The second survived because reaching it needs a volume whose attributes live in a block rather than in the inode, which means 128-byte inodes, and every fixture here used 256-byte ones. **Found by fuzzing** -- and on a pristine `e2fsck`-clean seed (s10, `mke2fs -I 128`), not a mutated one: an ordinary `listxattr` on ordinary media executed undefined behaviour. Regression cell in `Tests/run_bounds_tests.sh`, which is only an assertion under `make test-asan`. |
| `0063-lg-bsize-is-zero-during-mount-and-dividing-by-it-is-undefined` | **Undefined behaviour.** 0023's cache-coherency update locates the superblock's cached home block with `EXT4_SUPERBLOCK_OFFSET % bdev->lg_bsize`, and `lg_bsize` is still zero at that point: `ext4_mount()` calls `ext4_fs_init()` -- which writes the superblock to clear `VALID_FS` -- and only then `ext4_block_set_lb_size()`. So every read-write mount of every volume has divided by zero since 0023 landed. Harmless on arm64, which yields zero rather than trapping, and the cache is empty that early anyway; undefined nonetheless. Nothing can be cached before the block layer knows its block size, so the update is skipped. **Found by fuzzing**, in the read-write pass, on a pristine seed -- a mount and nothing else. Regression cell in `Tests/run_bounds_tests.sh`, an assertion only under `make test-asan`. |
| `0064-a-directory-with-a-hole-is-an-error-not-an-assertion` | **Bug fix, availability.** `ext4_fs_get_inode_dblk_idx_internal()` ended the extent path with `ext4_assert(*fblock || support_unwritten)`. Block 0 is the hole marker and the `support_unwritten = false` callers are the directory walks, so the condition is satisfied by any directory whose `i_size` claims more blocks than its extent tree maps -- a property of the bytes, not an invariant of the code. `CONFIG_DEBUG_ASSERT` ships, so on the installed extension a corrupt directory took the mount down from an `ls`. **Found by fuzzing** in the first sixty-second campaign, delta-minimized to four bytes: inode 14's `i_size_lo` turning a one-block directory into one claiming 16 MB on a 3 MiB volume. Now returns EIO, which every caller already propagates. Fixture `hostile/0003`. |
| `0065-an-xattr-walk-checks-its-bounds-before-it-dereferences` | **Bug fix, memory safety.** `ext4_xattr_is_ibody_valid()` read the header's magic, computed `min_offs` as `end - base` (an underflowed `size_t` when `base` is already past `end`), and read the first entry through `EXT4_XATTR_IS_LAST_ENTRY` -- all before establishing that any of them were inside the inode. `EXT4_XATTR_IHDR` places the header at `inode + 128 + i_extra_isize`, and that field comes off the medium. The loop's own bound check lived inside its body, after the fields had been read, so it guarded the entry after next. **Found by fuzzing**, minimized to ONE byte: a group descriptor's `bg_inode_table_lo`, moving the table 39 blocks into the metadata region. Both walks now bound before dereferencing. Fixture `hostile/0004`. |
| `0066-a-journal-that-replays-a-superblock-is-not-to-be-believed` | **Bug fix, corruption.** jbd2 replays by block number, and block 1 of a 1 KiB volume is the superblock. 0023 gave that branch a writer and a reload afterwards; nothing asked whether what landed is still a filesystem. A log staging arbitrary bytes for block 1 left `s_log_block_size` at 955747801, the next line shifted by it (undefined), and the flag edits below would have written that superblock back with RECOVER cleared -- a volume recovery could not fix, returned with no record that anything went wrong. `jbd_recover` now validates the reloaded superblock and fails with EIO, leaving RECOVER set for e2fsck; `ext4_sb_get_block_size` clamps the shift, because it is an inline accessor with no way to report and every caller shifts by what it returns. **Found by fuzzing**, in the read-write pass. Fixture `hostile/0005`. |
| `0067-a-directory-entry-length-off-the-medium-is-bounded-before-it-is-used` | **Bug fix, availability.** `ext4_dir_try_insert_entry()` walked a directory block using each entry's `rec_len` without ever bounding it. Three failures in one loop: the free-entry path passes `rec_len` to `ext4_dir_write_entry`, which asserts `entry_len <= block_size`, so 0xFFFF on a 1 KiB volume aborts the driver from a create; the split path computes `rec_len - sz` in uint16 and wraps when `name_len` says so; and the advance is `start += rec_len`, so zero spins forever while the mount is held -- the failure 0007 exists because of. **Found by fuzzing** in the first fuzz interlude of a soak, minimized to twenty bytes. Fixture `hostile/0006`. |
| `0068-a-bitmap-holds-as-many-bits-as-it-holds` | **Bug fix, memory safety.** `ext4_fs_init_block_bitmap()` marks a group's head blocks when materialising a bitmap for a `BLOCK_UNINIT` group. `bit_max` comes out of on-disk values and the loop WRITES one bit per iteration into a block-sized buffer; a bitmap holds `8 * block_size` bits and describes `blocks_per_group` of them. An out-of-bounds write reached from an ordinary inode lookup at mount. Clamped rather than refused -- the real head blocks are still marked, and refusing would make a recoverable volume unmountable. **Found by fuzzing**, two inputs in one two-minute campaign. Fixture `hostile/0008`. |
| `0069-an-htree-count-is-bounded-by-its-limit-before-it-sizes-a-checksum` | **Bug fix, memory safety.** `ext4_dir_dx_csum_verify()` checks the index block's `limit` against the block and then passes the `count` to `ext4_dir_dx_checksum()`, which is what sizes the region crc32c reads. Both are on-disk; nothing required `count <= limit`. Heap-buffer-overflow reached from `ext4_dir_find_entry` -- opening a file by name in an indexed directory. Verify now treats it as a checksum failure, which is the question the caller asked; the writer gets the same bound, because stamping a checksum computed over bytes outside the block is worse than not stamping one. **Found by fuzzing**. Fixture `hostile/0009`. |

Everything except 0001, 0003, 0010 and 0016 is a genuine upstream defect and worth
sending upstream — with two honest exceptions: 0043 and 0044 fix regressions that 0041
of this very series introduced (upstream has neither the batcher nor the bugs). 0002 and 0004 were found by running the write suite under
`-fsanitize=address,undefined` (`make test-asan`); 0005 by the crash-consistency
sweep; 0006 by reading the superblock state of volumes snapshotted out from
under a live mount; 0007 and 0008 together by the mounted-driver suite, which
caught a volume that had stopped answering and sampled the extension to find
out where it was; 0009 and 0011 by formatting across a range of volume sizes
and block sizes and handing every result to `e2fsck`.

0013 is what stopped Finder copying a file off an ext4 volume at all: macOS probes `com.apple.FinderInfo` on everything it touches, and an `EIO` there is
fatal to the copy. `cp` never showed it, because `cp` does not ask.

0012 is invisible unless a fixture has had its UUID changed after creation, which
is why one is built deliberately (`tune2fs -U` in `Tests/make_fixtures.sh`).
Reverting the patch and writing to that volume is the whole demonstration.

0009 and 0011 are both invisible at the sizes a casual test picks. 0009 needs a
volume that is *not* an exact multiple of the block-group size, and 0011 needs
1 KiB blocks specifically — at 2 KiB and 4 KiB the inode-table stride is already
a multiple of 8, so the alignment happens to be right by accident.

0007 and 0008 are one failure between them: 0008 is how the invariant gets
broken, 0007 is why breaking it costs the user their volume rather than one
failed syscall. Both are worth fixing — an assertion is not a plan for what to
do when it fails.

0005 is the most serious of the four. It is invisible to any test that does
not actually sever the write stream, because in normal operation the journal is
written, committed and checkpointed without ever being replayed. It only bites
on the recovery path — which is the one path that exists specifically to
protect data.

0004 is a good illustration of why the suite runs `e2fsck` after *every*
operation and why it runs under sanitizers: in an ordinary optimised build the
bug is invisible, because the freshly-allocated block happens to be zeroed and
the stale checksum still matches.
